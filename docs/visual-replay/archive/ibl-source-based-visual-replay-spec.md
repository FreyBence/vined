# IBL Visual Stimulus Replay — Source-Based Rendering and Display Specification

**Research/update date:** 2026-09-19  
**Purpose:** define how the ViNED/IBL visual-stimulus replay should use the original IBL rendering implementation and the best currently available display/lighting evidence, instead of relying on ad-hoc synthetic canvas choices.

**Implementation trace (2026-09-20):** [VR03 rendering and control semantics](ibl-renderer-semantics.md) distinguishes the protocol values below from the pinned workflow's effective behavior, including sigma/aperture and alpha blending, dynamic phase conversion, fixed grating orientation, wheel-reset timing, and the synchronization square. Use that trace when implementing the selected source revision; its static findings still require original-frame validation.

---

## 1. Scope and confidence levels

This document separates three kinds of information:

1. **Directly recovered IBL rendering parameters**  
   Values visible in the historical IBL `Gabor2D.bonsai` workflow or IBLRIG configuration.

2. **Published physical rig/display parameters**  
   Hardware geometry and stimulus properties reported by IBL publications or the LCD manufacturer.

3. **Approximate or unresolved values**  
   Values for which the original IBL sessions do not provide a verified session-specific calibration.

The goal is to reproduce the **visual input generated by the IBL task software as faithfully as possible** while keeping unknowns explicit.

## 3. Directly recovered IBL render-window settings

The historical `Gabor2D.bonsai` workflow configures the Bonsai shader window as follows:

```text
Width                 = 640
Height                = 480
VSync                  = On
SwapSync               = false
ClearColor             = Gray
WindowBorder           = Resizable
WindowState            = Fullscreen
DisplayDevice          = Second
TargetRenderFrequency  = 60
```

It also requests a graphics mode with:

```text
Red   = 8 bits
Green = 8 bits
Blue  = 8 bits
Alpha = 8 bits
Depth = 16 bits
Samples = 0
```

### Important interpretation

The workflow contains `Width=640` and `Height=480`, but also uses `Fullscreen`.

Therefore:

- **640 × 480 is a directly recovered workflow/window configuration value.**
- It is **not yet proven** that the physical LCD always received a literal 640 × 480 scanout.
- The operating system / GPU may have scaled the fullscreen render target to the panel's native resolution.
- The exact historical Windows/GPU scaling mode is still unresolved.

### Requirement for ViNED replay

Do not describe the current `720 × 720` replay canvas as an IBL property.

If replacing the current renderer, either:

- reproduce the original Bonsai render path directly, or
- explicitly implement a source-compatible 4:3 render target and document any resampling used to create stored videos.

## 4. Background color

The historical IBL workflow explicitly sets:

```text
ClearColor = Gray
```

in the Bonsai shader window.

The included BonVision `SphereMapping` workflow is also configured with:

```text
ClearColor = Gray
```

This is stronger evidence than the descriptive phrase "gray screen" in the papers: the renderer itself uses the named color `Gray`.

Bonsai uses the .NET `System.Drawing.Color` representation for this property. The named .NET color `Gray` is:

```text
RGB = (128, 128, 128)
Hex = #808080
```

### Replay requirement

For a standard 8-bit image representation, use:

```text
background_gray = 128
background_rgb  = (128, 128, 128)
```

unless a future session-specific framebuffer or calibration source proves otherwise.

### Important limitation

`RGB(128,128,128)` defines the **digital framebuffer value**, not the physical luminance seen by the animal.

The same digital value can produce different cd/m² on different displays or brightness settings.

Sources:

- IBL historical workflow:  
  https://github.com/int-brain-lab/iblrig/blob/iblrigv8/visual_stim/GaborIBLTask/Gabor2D.bonsai
- Bonsai `CreateWindow` implementation (`ClearColor` clears the framebuffer before rendering):  
  https://github.com/bonsai-rx/bonsai/blob/main/Bonsai.Shaders/CreateWindow.cs
- .NET `System.Drawing.Color.Gray`:  
  https://learn.microsoft.com/dotnet/api/system.drawing.color.gray

## 5. Original BonVision display geometry

The historical workflow does not simply draw a patch into a flat arbitrary pixel canvas. It uses BonVision view/mapping components.

Recovered components include:

```text
BonVision:Environment.OrthographicView.bonsai
    Left   = -180
    Right  =  180
    Bottom =  -90
    Top    =   90

BonVision:Environment.SphereMapping.bonsai
    ClearColor = Gray

BonVision:Environment.ViewWindow.bonsai
    Width  = 20
    Height = 15
    Translation.Z = -7

BonVision:Environment.NormalizedView.bonsai
```

The workflow then draws the grating through:

```text
BonVision:Primitives.DrawGratings.bonsai
```

### Why this matters

The current ViNED approximation maps a horizontal visual field directly onto pixels using a simple linear conversion.

The original renderer instead contains an explicit BonVision geometry/mapping chain. Therefore, the project should prefer the original BonVision mapping over a hand-written linear `degrees -> pixels` approximation whenever practical.

### Requirement

When porting the original visual renderer:

1. preserve the BonVision coordinate convention;
2. preserve the projection/view chain;
3. preserve the display aspect ratio;
4. preserve the original screen geometry;
5. validate that known positions such as `-35°`, `0°`, and `+35°` land where expected.

Do **not** interpret `ViewWindow Width=20`, `Height=15`, and `Translation.Z=-7` as centimetres without further source verification. They are recovered BonVision scene parameters; their physical interpretation depends on the BonVision mapping implementation.

BonVision repository:

https://github.com/bonvision/BonVision

Relevant operators:

- `Environment/SphereMapping.bonsai`
- `Environment/ViewWindow.bonsai`
- `Environment/OrthographicView.bonsai`
- `Environment/NormalizedView.bonsai`
- `Primitives/DrawGratings.bonsai`

## 6. Gabor stimulus parameters

The IBL behavioral task and historical task configuration support the following standard parameters:

| Parameter | Value |
|---|---:|
| Orientation | `0°` |
| Spatial frequency | `0.1 cycles/degree` |
| Gaussian sigma | `7°` |
| Initial azimuth | `-35°` or `+35°` |
| Correct target | `0°` |
| Wheel gain | `4 visual degrees/mm` for the standard task |
| Carrier phase | random per trial |
| Contrast | trial dependent |

The historical task configuration includes:

```text
STIM_ANGLE     = 0.0
STIM_FREQ      = 0.1
STIM_GAIN      = 4.0
STIM_POSITIONS = [-35, 35]
STIM_SIGMA     = 7.0
```

Source:

https://github.com/int-brain-lab/iblrig/blob/main/iblrig/base_choice_world_params.yaml

Historical source code also exposes per-trial values such as:

```text
stim_angle
stim_freq
stim_gain
stim_phase
stim_sigma
```

### Spatial frequency

Use:

```text
0.1 cycles / visual degree
```

This means one complete sinusoidal period occupies:

```text
10 visual degrees
```

Do not use an arbitrary "number of stripes per patch."

### Sigma

Use the recovered/task value:

```text
sigma = 7 visual degrees
```

Do not use the previous synthetic approximation of `sigma ≈ 30 px` as if it were an IBL value.

If a Python implementation requires pixels, convert angular sigma through the **same display mapping used by the renderer**, not through a separate independent scale.

### Phase

The IBL behavior paper specifies random carrier phase.

If session-specific `stim_phase` is available from raw task data, use it.

Only use deterministic synthetic phase when the original phase cannot be recovered, and mark such trials as reconstructed rather than exact.

## 7. Physical screen and placement

The standardized IBL task used an LG Display `LP097QX1` panel.

IBL reports:

- screen approximately **8 cm in front of the animal**;
- centered relative to the eyes;
- approximately **102° horizontal visual coverage**;
- display approximately **9.7 inches / 246 mm diagonal**.

Source:

International Brain Laboratory et al. (2021), *Standardized and reproducible measurement of decision-making in mice*:

https://doi.org/10.7554/eLife.63711

Open-access version:

https://pmc.ncbi.nlm.nih.gov/articles/PMC8137147/

IBL wheel/stimulus-position documentation:

https://docs.internationalbrainlab.org/notebooks_external/docs_wheel_screen_stimulus.html

### LCD manufacturer specification

For the LG Display `LP097QX1-SPC1`, the manufacturer specification reports:

| Property | Specification |
|---|---:|
| Native resolution | `2048 × 1536` |
| Aspect ratio | `4:3` |
| Pixel pitch | `0.192 × 0.192 mm` |
| Active display area | `196.608 × 147.456 mm` |
| Color depth | `8-bit/channel` |
| Typical white luminance | `440 cd/m²` at the specified LED current |
| Frame frequency used in optical specification | `60 Hz` |
| Nominal grayscale gamma | `2.2` |

Manufacturer specification:

https://www.beyondinfinite.com/lcd/Library/LG-Display/LP097QX1-SPC1.pdf

### Important limitation

The panel's `440 cd/m²` value is a **manufacturer white-luminance specification at a defined backlight drive condition**.

It is **not evidence that IBL ran the task at 440 cd/m²**.

## 8. Physical luminance / screen brightness

The original standardized-behavior publication does **not** give a single calibrated screen-luminance value that can be assumed for every laboratory/session.

A later IBL-associated study explicitly states that:

- screen brightness was **not well standardized across laboratories**;
- no published illumination value was available in the original standardized behavior paper;
- retrospectively, the authors determined an **average screen brightness of 29.4 cd/m²**.

Source:

Ghani, Yang & International Brain Laboratory (2026),  
*Active sensing during a visual perceptual decision-making task*, iScience 29(6):115976.

https://doi.org/10.1016/j.isci.2026.115976

Open-access version:

https://pmc.ncbi.nlm.nih.gov/articles/PMC13200138/

### How to use 29.4 cd/m²

Treat:

```text
29.4 cd/m²
```

as a **best available historical average**, not as an exact per-session calibration.

#### For digital replay used as model input

Do not attempt to encode `29.4 cd/m²` directly into the video file.

Use the recovered framebuffer values and contrast relationships, especially:

```text
mean/background gray = RGB(128,128,128)
```

Physical luminance is not preserved by an ordinary MP4 image representation.

#### For a physical experimental replay

If the goal is to recreate an IBL-like physical visual environment on a real monitor and no rig-specific calibration is available:

1. use the original gray framebuffer value;
2. measure the display with a photometer/luminance meter;
3. a mean-screen luminance near **29.4 cd/m²** can be used as a documented historical approximation;
4. record the measured value;
5. do not claim it reproduces the exact original session.

If session/lab-specific calibration becomes available, it must override this average.

## 9. Gamma

Two different facts must not be conflated.

### Panel specification

The LG panel datasheet gives a nominal grayscale gamma of:

```text
gamma = 2.2
```

### IBL task calibration

The inspected historical `Gabor2D.bonsai` workflow did **not** reveal an explicit session-specific gamma-correction stage.

Therefore:

- the panel's nominal `2.2` gamma is useful hardware information;
- it does **not** prove that each IBL rig had an experimentally measured gamma of exactly 2.2;
- it does **not** prove that the framebuffer values were calibrated to linear luminance.

### Replay policy

For CLIP/video reconstruction, preserve the original digital rendering behavior rather than applying a newly invented gamma correction.

For physical replay, measure the actual monitor response if luminance fidelity matters.

---

## 10. Ambient lighting

No reliable session-wide specification was found for:

- room illuminance in lux;
- cabinet internal illuminance;
- external room light level;
- exact adaptation illumination around the display.

The standardized apparatus was housed in an acoustical cabinet, but this does not by itself establish a numerical ambient-light condition.

### Requirement

Do not invent an ambient-light value.

For the current ViNED digital replay, ambient room light should not be encoded into the stimulus frames unless a source explicitly supports it.

For a new physical reproduction:

- use a controlled environment;
- measure and record ambient illuminance;
- distinguish this new experimental condition from recovered IBL parameters.

---

## 11. Refresh rate and timing

The historical Bonsai workflow requests:

```text
TargetRenderFrequency = 60
VSync = On
```

The LG panel specification is also compatible with a 60 Hz frame rate.

### Requirement

When replaying the original renderer:

- treat **60 Hz** as the source render/display cadence;
- preserve frame-synchronous changes;
- preserve the IBL frame2TTL / photodiode timing information whenever alignment to neural data is required.

The current ViNED output video may still be stored at another FPS for downstream processing, but this should be an explicitly documented resampling step rather than an assumed original display rate.

## 12. Recommended implementation strategy for ViNED

### Option A — execute the historical renderer

This is the preferred fidelity path.

1. Prepare a compatible environment for historical IBLRIG/Bonsai.
2. Use the `iblrigv8` `Gabor2D.bonsai` workflow.
3. Supply recovered trial parameters through the same OSC/task interfaces where practical:
   - position;
   - contrast;
   - spatial frequency;
   - angle;
   - sigma;
   - phase;
   - gain.
4. Supply wheel motion according to the original task convention.
5. Capture/export rendered frames.
6. Associate each frame with the original session timestamp.
7. Convert the captured frames to the storage format used by ViNED.
8. Record the source commit, Bonsai version, BonVision version, and all deviations.

### Option B — source-faithful Python port

If running historical Bonsai is impractical, port the original workflow.

The Python port must reproduce, rather than replace:

- gray clear color;
- the IBL/BonVision geometry;
- `DrawGratings` behavior;
- contrast;
- phase;
- frequency;
- Gaussian/aperture handling;
- initial position;
- wheel-driven movement;
- freeze behavior;
- 60 Hz source timing;
- display aspect ratio.

The port should be validated against frames rendered by the original workflow for synthetic reference inputs before being called source-faithful.

## 13. Parameters to change in the existing ViNED replay

The following previous project choices should no longer be treated as IBL specifications.

### Replace / deprecate

```text
720 × 720 canvas
```

Reason: historical IBL workflow uses a 4:3 render configuration and fullscreen output.

```text
hand-written Gabor frequency in pixels
```

Reason: original spatial frequency is `0.1 cycles/degree`.

```text
sigma = 30 px
```

Reason: standard IBL task value is `7°`, and conversion should happen through the original display mapping.

```text
simple 102° -> 720 px linear mapping
```

Reason: the historical workflow contains a BonVision sphere/view mapping chain.

### Keep, but reclassify as source-supported

```text
background = 128
```

This is now supported by the original renderer's `ClearColor=Gray`, provided the target is an 8-bit RGB representation.

## 15. Remaining unresolved points

The following are still not sufficiently verified for exact session reconstruction:

- exact historical Windows/GPU fullscreen scaling from the Bonsai `640×480` configuration to the native `2048×1536` panel;
- exact per-rig monitor brightness/backlight setting;
- exact per-rig measured luminance;
- exact per-rig gamma calibration;
- ambient illuminance;
- whether all Reproducible Ephys sessions used precisely the same visual-stimulus software revision;
- session-specific display calibration and projection corrections;
- exact monitor driver/scaler behavior.

These unknowns must remain explicit.

## 17. Acceptance checks before calling the renderer source-faithful

A source-faithful implementation should be checked against the historical Bonsai workflow using controlled synthetic inputs.

At minimum compare:

- blank gray frame;
- 0% contrast;
- 6.25%, 12.5%, 25%, 50%, and 100% contrast where applicable;
- left and right initial positions;
- centered stimulus;
- spatial frequency;
- sigma/aperture;
- several known phases;
- inward motion;
- outward/error motion;
- freeze behavior;
- edge clipping;
- aspect ratio;
- source frame cadence.

Comparison should be image-based and geometric, not only visual inspection.

Only after this validation should the Python renderer be described as a port of the original IBL stimulus renderer.

---

## 18. Source hierarchy

When sources disagree or provide different levels of detail, use the following priority for reconstruction:

1. **Session-specific raw task parameters**
2. **Historical IBL rendering source used by the relevant task version**
3. **IBLRIG task configuration**
4. **IBL protocol/publication**
5. **Hardware manufacturer specification**
6. **Later retrospective measurements**
7. **Project approximation**

This hierarchy prevents a hardware nominal value or later average from silently replacing a session-specific experimental value.

## 20. Bottom-line implementation decisions

For the next ViNED renderer revision:

- **Use the original `Gabor2D.bonsai` workflow as the authoritative rendering reference.**
- Pin/document the historical Bonsai/BonVision versions where possible.
- Use **gray `RGB(128,128,128)`** as the digital background.
- Use **0.1 cycles/degree** spatial frequency.
- Use **7° sigma** unless a session-specific value overrides it.
- Use trial-specific contrast and phase whenever recoverable.
- Use the original BonVision geometry instead of a new arbitrary square canvas.
- Treat **60 Hz** as the original target render cadence.
- Keep the distinction between the **640×480 workflow render configuration** and the **2048×1536 native LCD panel**.
- Treat **29.4 cd/m² only as a retrospective cross-rig average**, not as an exact IBL session luminance.
- Do not invent ambient illumination or session gamma calibration.
- Validate any Python port directly against output from the historical Bonsai workflow.
